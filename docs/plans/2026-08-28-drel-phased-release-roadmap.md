# Drel 产品版本路线图

> **唯一版本依据。** 本文定义 Drel 对外产品版本、范围边界、进入
> TestFlight 和提交 App Store 的条件。`docs/release/` 下的清单记录某个
> 构建的执行证据，不改变本文的产品范围；SDK、原型和历史计划中相冲突的
> 描述，以本文为准。
>
> **更新时间：** 2026-09-09。App Store Connect 的状态会随 Apple 处理而
> 变化；提交、TestFlight 分发或审核前必须重新读取实际页面，不能只依据本文。

## 1. 版本号与构建号

- **版本号**是用户看到的产品承诺，例如 `2.0.0`。
- **构建号**是 Apple 上传流水号，例如 `62`；它只会递增，不能预先承诺。
- 一个版本可以有多个 TestFlight 构建；只有通过对应版本全部验证门的**精确
  构建**可以提交审核。
- 不允许把后一阶段代码、宣传文案或入口偷偷带进前一版本。提前某项能力时，
  必须把它连同风险、测试和审核说明一起移动到目标版本并更新本文。

候选。它只用于当前 1.0 稳定化与真机验收。

## 3. 总路线

| 对外版本 | 名称 | 用户得到什么 | 明确不包含 |
| --- | --- | --- | --- |
| **1.0.x** | 推送与网页目的地 | 开发者复制推送地址，收到通知，在 Drel 中打开明确指定的 HTTPS 页面。 | Bridge、网页应用安装、离线包、公开目录。 |
| **1.1.0** | 推送工作流完善 | 更完整且真实的推送示例、复制/重置地址、官方与自托管通道的清晰切换。 | 应用入口、离线下载、网页调用原生能力。 |
| **1.2.0** | 常用入口与容器操作 | 保存常用网页入口；全屏页具备清晰的返回、收藏、刷新、复制与分享操作。 | 我的应用、离线包、Bridge。 |
| **1.3.0** | 我的应用与默认启动 | 把符合规范的网页添加为“我的应用”；可设默认启动应用。 | 离线包下载、后台更新、Bridge。 |
| **1.4.0** | 私有离线应用 | 用户主动安装并管理经过校验的离线网页应用包。 | 公开应用市场、静默更新、Bridge。 |
| **1.5.0（决策门）** | 受控原生能力 | 仅在单独安全与审核评估通过后，为已安装应用开放声明式、可撤销的能力。 | 通用 JS Bridge、远程下发新原生功能、推送直接授权。 |
| **1.6.0** | 多应用工作区 | 多个私有应用的切换、存储、更新、回滚与删除。 | 公共目录、UGC、第三方应用分发平台。 |
| **2.0.0** | 保留 | 仅在出现兼容性迁移、账户/数据模型重构，或产品契约明显改变时再定义。 | 不能只因新增一个功能而升级为 2.0。 |

`1.4.0` 与 `1.5.0` 是建立在 `1.3.0` 应用身份之上的两条**独立发布线**：
离线包先解决“网页内容能否可靠留在本机”，Bridge 才讨论“网页是否可请求原生能力”。
它们不得合并到一个审核构建；Bridge 也不依赖离线包已经发布。

## 4. 1.0.x — 推送与网页目的地

### 产品承诺

1. 用户安装 Drel 后能复制官方推送地址，开发者可发送消息。
2. 推送在前台、后台、锁屏下表现一致；点通知打开精确 URL。
3. `mode=immersive` 的展示策略在通知点击、收件箱、详情和正文链接之间保持一致。
4. 自托管通道可以与官方通道并存；每条消息保留可信来源标记。

### 当前边界

- Store 构建是容器模式：不注入网页可调用的原生 Bridge，不让网页请求原生权限。
- 支持普通 HTTPS 页面和推送目的地；不声称网页已被安装为离线应用。
- 原始缓存、调试页、网关调试、未完成的应用中心不出现在 Store 导航和商店素材中。

### 1.0.1 的放行条件

| 验收项 | 必须证明 |
| --- | --- |
| 自动化 | Release 构建、容器边界扫描、路由/载荷/无重复发送测试全部通过。 |
| 真机 TestFlight | 前台、后台、锁屏、铃声、通知点击路由、沉浸式展示、仅一次投递、撤销/重置各有记录。 |
| 商店 | 精确构建已处理；出口合规、隐私、截图、审核说明、审核附件均与该构建一致。 |
| 提交 | 只有完成上述项目并获得当次明确确认后，才执行“提交审核”。 |

## 5. 1.1.0 — 推送工作流完善

### 范围

- 每一类**已支持**的推送示例都能复制实际参数；示例不展示未实现能力。
- 收件箱、详情和系统通知中的复制动作遵循同一份内容选择规则。
- 用户可以复制地址、复制 Key、重置地址；重置必须先精确撤销旧身份再生成新身份。
- 首页清楚显示当前通道（官方 / 自托管）、复制的地址以及切换入口。

### 不能提前带入的内容

- 不出现“下载应用”“离线可用”“安装包”或网页原生权限。
- 不因自托管而把 Drel 的 APNs 私钥、用户设备令牌或其他私密凭据暴露给部署者。
- 不把“更多菜单”变成缓存或开发者调试面板。

### 进入 TestFlight 的条件

复制、重置、官方/自托管切换、消息来源归档、URL 路由都通过模拟器回归；随后用真机验证
APNs 送达、点按路由和旧地址失效。测试通过后才创建 `1.1.0` 的新递增构建。

## 6. 1.2.0 — 常用入口与容器操作

这是普通网页的易用性版本，不把网页伪装成已安装应用，也不引入离线或 Bridge。

### 常用入口

| 类型 | 用户操作 | 首页表现 | 启动行为 |
| --- | --- | --- | --- |
| **常用入口** | 在网页全屏菜单选择“加入常用”。 | 首页“常用”卡片，保存标题、图标和 URL。 | 仅手动一键打开；不自动保存临时页面状态。 |

### 全屏页交互

- 常驻：返回（有网页历史则后退，无历史则退出）、加入/取消常用、更多。
- 更多：刷新、复制链接、系统分享、在 Safari 打开、页面信息。
- 不显示：原始 Cache、下载调试、Bridge 调试、任意网页的“授予原生权限”。

### 安全与数据规则

- 常用入口不自动保存带 token、一次性参数或敏感路由的完整 URL。
- 推送只负责定位，不能授权网页操作。

### 1.2.0 放行条件

1. 新装、升级、删除入口、回退首页均有模拟器测试。
2. 仅允许用户主动添加；推送、网页脚本或远程配置不能自动创建入口。
3. Store 素材和审核说明只描述“保存常用网页”，不声称离线或原生能力。
4. 新 TestFlight 构建在真机验证启动、通知路由与现有推送身份不回归。

## 7. 1.3.0 — 我的应用与默认启动

这是网页的**应用概念**，但它仍不是离线下载，也不是 Bridge。

### 范围

- 用户从符合规则的 Manifest/应用描述明确添加一个网页应用。
- 采用标准 Web App Manifest 作为名称、图标、启动页、范围与展示偏好的来源；
  Drel 兼容范围见 `docs/api/drel-web-app-manifest-profile.md`。
- 首页出现独立应用卡片，可查看来源、版本和入口页。
- 已添加应用在全屏页才显示“应用信息、设为/取消默认启动、从首页打开”。
- 默认启动保存应用的稳定身份和受信任起始页；冷启动打开它，而推送始终优先。

### 安全与数据规则

- 不默认保存带 token、一次性参数或敏感路由的完整 URL。
- 如果用户明确选择“将当前页设为应用首页”，需展示最终 URL，移除凭据和临时参数，并限制为已确认的同源路由。
- 推送、网页脚本或远程配置都不能自动添加应用、设置默认启动或改变入口页。

### 1.3.0 放行条件

新装、升级、删除应用、默认启动、推送优先级与回退首页均有模拟器测试；精确 TestFlight
构建在真机验证启动、通知路由和现有推送身份不回归。

## 8. 1.4.0 — 私有离线应用

### 范围

- 已添加应用可以由用户主动选择“下载以供离线使用”。
- 应用详情只提供明确的“下载离线包 / 更新离线包 / 删除离线包”操作；已安装状态显示版本和实际占用空间，删除前说明会移除本地网页资源，删除后回退联网打开。
- 页面显示人能理解的状态：未下载、下载中、离线可用、有更新、下载失败；不展示技术性的 Cache。
- 每个包必须有稳定应用身份、HTTPS 来源、签名、资源哈希、版本、大小和更新来源。
- Web App Manifest 继续负责应用展示；离线资源清单负责精确文件校验，两者不可互相替代。
- 下载完成后写入应用管理的持久化存储；校验完整后才原子切换版本，失败继续使用旧版本。

### 构建边界

- 当前 `1.0.x` Store Release 使用 `DREL_RELEASE_MINIMAL_SETTINGS` 隐藏“我的应用”与离线管理；不得为补丁版本提前解除这个开关。
- `1.4.0` 应使用独立的 Store 构建配置，只解除上述最小设置开关以展示已验收的应用/离线管理；`DREL_CONTAINER_ONLY` 必须继续保留，网页不能因离线安装而获得 Bridge。

### 当前实现证据（2026-09-09）

- 已建立独立 `Drel14Store / Drel14Release`，版本号为 `1.4.0`；模拟器 Release
  构建成功，编译条件只有 `DREL_CONTAINER_ONLY`，没有解除 Bridge 边界。当前本地签名候选为
  `Drel 1.4.0 (63)`，尚未上传 TestFlight。
- 父 Manifest 的签名载荷已包含标准 Web App Manifest 的 URL 与 SHA-256；网关
  导入会真实下载并验证准确字节、重定向、作用域、同源图标及 `drel_offline` 一致性。
- 离线包由用户在应用详情中明确下载、更新或删除；状态显示版本与实际空间，启动不会
  隐式安装或更新。
- 模拟器测试已证明安装完成后网络运输层不可用时，入口 HTML 与 CSS 仍从本地强离线包
  解析；安装失败、中断、错误哈希会保留旧版本。
- 推送与应用列表共用同一解析结果：未安装时使用真实在线页面，绝不打开资源清单；用户
  主动安装完成后，`appId + route + params` 才落到本地入口。
- 一键静态发布门为 `tools/verify-drel-14-offline-release.sh`；真机验收表为
  `docs/verification/drel-14-physical-device.md`。尚未完成真机表、未上传 1.4.0，不能描述为已发布。

### 红线

- 不提供公开搜索、推荐、分享、评分、发布者后台或第三方应用市场。
- 不允许静默安装或静默更新；首次只允许前台且用户主动更新。
- 不以 WebKit/HTTP 缓存冒充离线安装；删除必须说明会删除哪些包和本地数据。

### 1.4.0 放行条件

签名、哈希、断网启动、中断下载、回滚、存储清理、来源/密钥变化确认均有自动化验证；精确
TestFlight 构建完成从安装到断网启动的真机验收，并准备可供审核人员使用的演示应用。

## 9. 1.5.0 — 受控 Bridge（尚未承诺开发）

本版本是**决策门**，不是“离线包完成后自动附送”的功能。只有下列条件全部满足，才创建
实现计划和 TestFlight 构建：

1. 每个应用通过 Manifest 声明所需能力；能力按应用、域名和用途分别授权、可撤销、可审计。
2. 所有敏感能力由用户在应用内主动触发；通知和 URL 参数不能直接批准或执行。
3. 没有任意脚本注入、通用命令通道或远程动态新增原生能力。
4. 完成安全评估、隐私说明、App Review 演示和真机权限验证后，才讨论提交审核。

它最早可在 `1.3.0` 验证通过后独立立项；即使 `1.4.0` 离线包延期、被拒审或需要修复，
也不能把离线包与 Bridge 打包来“顺带测试”。反过来，Bridge 被拒审或需要重做时，也不影响
`1.4.0` 的纯网页离线发布线。

## 10. 1.6.0 — 多应用工作区

在 1.4.0 被实际审核和使用验证后，再加入多应用列表、切换、默认应用、每应用存储、更新、
回滚和删除。任何公共目录、跨用户分享、UGC 或第三方发布者流程都不属于 1.6.0；那会是一个
新的平台产品决策，而不是普通功能迭代。

## 11. 提前功能的判定表

| 想提前的功能 | 最早可进入 | 不可提前到 |
| --- | --- | --- |
| 全屏页返回、收藏/常用、刷新、复制、分享 | 1.2.0（也可作为不改变协议的 1.1.0 小改动单独评估） | 不需要等待离线或 Bridge。 |
| 首页常用入口 | 1.2.0 | 不能以“缓存列表”替代。 |
| 我的应用、默认启动 | 1.3.0 | 不能默认记住任意完整 URL。 |
| 离线下载、更新、删除包 | 1.4.0 | 不能混入 1.2.0 或 1.3.0。 |
| 原生 Bridge / 权限 | 1.5.0，且需重新决策；只依赖 1.3.0 | 不与 1.4.0 离线包打包，也不能借应用/离线名义提前开放。 |
| 多应用私有索引 | 1.6.0 | 不能变成公共市场。 |
| 大版本升级 | 2.0.0 | 仅在需要不兼容迁移或产品契约改变时发生。 |

## 12. 每个版本固定发布流程

1. 在本文冻结该版本范围与明确排除项。
2. 写对应实现计划、测试矩阵、迁移与回滚方案。
3. 完成模拟器和 Release 边界验证；新建递增构建并上传 TestFlight。
4. 真机 TestFlight 只验证无法由模拟器证明的推送、锁屏、权限、升级与离线行为。
5. 更新商店文案、截图、隐私与审核说明，使其只描述该精确构建实际具备的能力。
6. 由产品所有者对精确版本和构建给出当次确认后，才提交 App Review。
